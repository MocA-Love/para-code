OpenCode 側の調査結果（追い風の事実）

  • TUI 起動時に必ず HTTP サーバーを内包。--port 固定可 → 監視も制御も単一経路で可能
  • GET /event（SSE）でメッセージ・実行状態・権限確認（permission）・質問イベントが取れる
  • POST /permission/:id/reply 等で承認に API 直答できる（TUI キー注入不要 = Codex daemon と同等品質）
  • モデル一覧は GET /config/providers、送信時にモデル指定可
  • Plugin システム（JS/TS）で全イベントフック可 → Claude hooks 相当の「/agent-hook へ POST」プラグインを作れる
  • Para Code 側の正規化テーブルに既に OpenCode 由来イベント名（task_complete, permission.ask 等）が登録済み
注意点: リリース頻度が非常に高く API 改変が日常的（permission API は直近で移行済み）。 ポート発見の公式機構がないため、自前ランチャーでの固定が必要。

どう対応するか：推奨アーキテクチャ

「ランチャー + SSE ライブクライアント」を主経路、「hook プラグイン」を補助経路

ターミナル → 自前ランチャー(resources/paradis/bin/opencode) opencode --port <確保したポート> で起動 ├─ pcx/<paneToken>.endpoint.json に port/auth を書き出し ← 検出 └─ ~/.config/opencode/plugins/para-code-hook.js を冪等設置 ← 補助 └─ 全イベントを /agent-hook?pane=<token> へ POST shared process ├─ 既存 hook バス → サイドバー状態表示（ほぼ無変更で動く） └─ 新規 paradisOpencodeLiveClient.ts ← SSE 接続 live 状態 / 承認・質問 interaction / モデルカタログ を relay へ供給 → モバイルへは既存プロトコルで配信
  • サイドバー状態表示: hook プラグインだけで成立（既存正規化テーブルが受け入れ済み）
  • モバイルの承認・モデル切替: HTTP API 直答（Codex daemon 方式と同じ品質）
  • フォールバック: プラグイン未導入でも transcript 補完経路で最低限は動く設計

実装フェーズ

Phase 0 — 実機スパイク （半日〜1日 / 最優先）
  1. opencode serve / TUI 内蔵サーバーの挙動確認（--port 0 可否、プロセス構成）
  2. /doc の OpenAPI spec で permission・question・providers エンドポイントを実確認
  3. SSE イベント payload 収集 → ライブ状態マッピング表作成
  4. plugin からの外部 POST 動作とイベント名の一致確認
  5. TUI 操作と API 応答の共存（first-response-wins）検証
Phase 1 — PC 側 型・検出基盤 （型ユニオン拡張で網羅）
  • ParadisAgentKind に 'opencode' 追加 → 型エラーが出た箇所を順次解消
  • home 解決 / hook プラグイン設置 / 所有判定 / CLI コマンド解析 / worktree 既定コマンド / 表示名 'OpenCode'
Phase 2 — PC 側 ライブ統合 （新規ファイル中心・2〜3日）
  • resources/paradis/bin/opencode ランチャー（endpoint ファイル書き出し）
  • opencodeBridge/node/paradisOpencodeLiveClient.ts 新規：SSE → live 状態・interaction 化（ID 形式 opencode:s:<id>）・モデルカタログ
  • relay へのディスパッチ組込み（承認 API 直答・質問回答・送信・settings-update）
Phase 3 — PC 版 UI 統合 （サイドバー等）
  • Workspaces ビューの状態表示は Phase 1 の hook 経由で自動動作のはず → 実機確認中心
  • Resume エディタのバッジ CSS、ブラウザバインディング検出
Phase 4 — モバイル版 （PC とは別コミット・1.5〜2日）
  • 必須: 起動メニュー追加、modelPill 分岐、PTY フォールバック承認キーの実測値
  • 推奨: ブランド色、Live Activity 表示名、activity provider 追加
Phase 5 — テスト・検証・リリース （0.5〜1日）
  • parity テスト維持 / typecheck → eslint → compile / iPhone・iPad 両実機検証
  • 更新履歴: PC 版 changelog + モバイル版 MOBILE_CHANGELOG に記載

合計想定工数: 約 5〜7 日（Phase 0 の結果次第で Phase 2 が増減）
